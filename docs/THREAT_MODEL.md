# THREAT_MODEL.md (draft v1)

## Assets
Photo/video contents, thumbnails, filenames, EXIF (incl. GPS), capture dates, album names, user passwords, master and recovery keys.

## Actors
Admin (trusted to administer, **not** to see content), regular users, other tailnet members, a passive attacker with a copy of the disk/backups, an attacker who compromises the server process, a network attacker, a malicious or curious VPS provider.

## What the server stores and learns
- **Learns:** e-mail addresses, who is admin, account creation, last sign-in time per person, an admin activity log of the last 500 administrative events (invites, limit and role changes, disabling, deleting) and, kept apart so they cannot push those out, the last 500 times someone signed out their own devices (metadata only), and IPs only transiently in the rate limiter (the server writes no request logs, and the only secret it logs is the one-time setup token), number of items, ciphertext sizes (approximate file sizes, photo vs. video guess), upload/delete times, album structure (how many albums, which items are in which album), quota usage, whether two-step sign-in is on, its authenticator secret (see Two-step sign-in below), the account's passkeys (see Passkeys below) and keyed hashes of the unused recovery codes, and the last 50 notices per account (new sign-ins with the device's own label, as in the device list, and the time; unfinished password steps with their time; at most 90 days), and when a finished item's encrypted metadata, thumbnail or preview is replaced (so that, and roughly when, a photo was edited or its date or place changed; never what changed, docs/EDITING.md).
- **Never receives:** passwords, `authKey`'s preimage, KEK, master key, recovery key, item keys, plaintext or filenames, EXIF/GPS, capture dates, album names, edits (turn, crop, a changed date or place, or the values before).

## Scenarios

| Threat | Outcome |
|---|---|
| DB + blobs stolen (disk, backup, provider) | Only ciphertext. Offline password guessing requires the Argon2id (client params) work per guess against `argon2id(authKey)`. Weak passwords are still guessable; recovery keys are 256-bit. |
| Admin snoops | Cannot decrypt anything; can disable/delete accounts and see the metadata above. Admin cannot reset a password in a way that preserves access to data: reset would require the recovery key. |
| User A tries to reach user B's data (IDOR) | Every query is scoped to the session's `user_id`; object IDs are random 128-bit; foreign IDs return 404. Even if bypassed, the data is encrypted under B's keys. Tested at API and UI level. |
| Network attacker | TLS from the operator's reverse proxy (any; OrbStack locally). HSTS. Behind Tailscale Serve the tailnet is WireGuard encrypted as well. |
| Tampering/swapping ciphertext | AEAD with AD binding item id, segment index, counts and total size. Failure -> nothing displayed. |
| Replaying older ciphertext (rollback) | The AD binds each blob to its item or owner, not to a point in time, so a malicious server can hand out an older authentic copy it kept: an item's metadata from before a place was removed or an edit was made, the old thumbnail and preview, an album's old name, an older people document. For item metadata the web and Android apps defend this: the metadata carries a version raised at every change (`mv`, docs/CRYPTO.md), each device remembers the highest version seen per item and never shows a lower one (the newer metadata stays while known; otherwise the item is marked stale and a default download, share or save gives a copy without a place, never the original). Limits: a device that never saw the newer version (a new device, or after sign-out, or an item beyond the 10,000 remembered) accepts the older one; a change made by an app version from before `mv` doesn't raise it; thumbnails and previews, album names, the people document and the search index carry no version and can still be rolled back; the Mac app does not check versions. |
| Brute-force login | Attempts are counted atomically before the Argon2 check: 30 per source address and 10 per (account, source address) per 15 minutes, as a hard block (no back-off); IPv6 sources are grouped by /64. Argon2id on the server side too, with at most 4 verifications in flight; sign-ins and recoveries from unknown browsers wait in a queue of at most 16 and get 503 when it is full (known browsers are counted apart, so they never fill that queue, and each account has at most 2 checks from known browsers running or waiting at once; more get 503). The password proofs of signed-in sessions (changing the password or two-step sign-in, a new recovery key, deleting the account) wait in that same separate lane under the same per-account cap, leave it when the client has gone, and are limited to 30 per account per 15 minutes, right or wrong, and a request whose client has gone leaves the queue without being checked. There is deliberately no per-account ceiling across all sources, because that would let an attacker lock the real user out from many addresses; the cost is that a widely distributed guesser is limited only by the Argon2 work and the per-source buckets. Browsers that have signed in before carry a signed device cookie (HMAC over user id and password hash; invalidated by a password change) and are counted in a separate per-account bucket (20 per 15 minutes) instead of the per-source ones, so strangers sharing a proxy address (Tailscale Serve, Cloudflare Tunnel, `TRUST_PROXY=0`) cannot lock the real user out from a known browser. Account recovery (`/api/auth/recover/start`) uses the same scheme: 30 per source and 10 per (account, source address), or 20 per account from a known browser. Limitation: a *new* browser or device can still be blocked from signing in or recovering for up to 15 minutes while someone is guessing from the same shared source; a stolen device cookie only buys 20 password and 20 recovery-key guesses per 15 minutes. |
| Stolen password (two-step sign-in on) | The password step returns no session, no cookie, no device cookie and none of the account's key material (wrapped master key, private key): only a random pending token (stored hashed in memory), valid 5 minutes, bound to the account and to the password hash it was issued for (a password change, recovery or admin reset ends it), good for 5 wrong codes and one right one (a passkey's answer counts the same; see Passkeys below). Codes are counted before they are checked: 5 per account per 15 minutes and 20 per account per day (across all sources, because 6 digits are few; this ceiling is deliberate here, unlike the password's), plus a bucket per (source, account), so one account's own sign-ins from a shared source never use up the second step for others there; a password change or an account recovery ends the pending sign-ins but keeps the count, so neither a session that has the password nor the recovery key can reset the code limits again and again (only a right code does). A code is compared in constant time against the current, previous and next 30-second step and never accepted twice: the step of the last accepted code is stored and every code up to it is refused, atomically in the database. A recovery code is 80 random bits, stored as an HMAC under a key derived from the server's secret file, and deleted when used (atomically, so two requests can't both use it). Turning two-step sign-in off, making new recovery codes, changing the password, making a new recovery key and deleting the account need the password proof and a current code (or a recovery code, or a passkey), so a signed-in session and the password alone can't take the account over or delete it; an app that sends no second step is told so (`second_step_required`). The codes entered on a signed-in device are counted in buckets of their own of the same size (5 per 15 minutes, 20 per day), so wrong codes at sign-in, which is all someone with only the password can enter, never keep a signed-in device from these changes; a right code there clears both. A password step that is not followed by a right code (it expires, wears out, is pushed out by newer ones, or is ended by a password change) is shown on the account's devices once it can no longer finish: "Your password was used to start a sign-in that wasn't finished" (at most one such notice per hour per account; the notice is stored at the password step and deleted again if the code follows; it is shown 5 minutes after the first unfinished password step, and repeating the password step does not postpone it). Limits: someone who has the password can keep the real person from finishing a new sign-in for up to a day by entering wrong codes (devices already signed in are not affected; changing the password on one of them, which takes a right code, ends it); an administrator, or the server console (`reset-2fa`), can turn two-step sign-in off for an account, which then signs in with the password alone; the person's devices show a notice that it happened. Unlocking a device that is already signed in (password, fingerprint, Touch ID) never asks for a code: it never asks the server. |
| New sign-in or admin reset unnoticed | The account's other signed-in devices show a notice (live updates, else at the next start): "New sign-in: device, time", that an administrator turned off two-step sign-in, (two-step sign-in on) that the password was used for a sign-in that wasn't finished, and that two-step sign-in was changed from another device (an authenticator app or passkey added or removed, new recovery codes, two-step sign-in turned off; with that device's label and the time, shown on the devices signed in at the time, not on the one that made the change). The device label is what the device calls itself, so a thief's own app could name itself anything; the notice still shows that a sign-in happened. Dismissed on one device, it is dismissed on all, but only a device that is shown it can dismiss it: never the session the sign-in started, and a sign-in only on devices signed in before it (ordered by the notices themselves, so two sign-ins in the same second are not shown each other). So whoever signs in with a stolen password cannot take down the notice about that sign-in, from that session or a later one. Limits: a session can dismiss the notices about all later sign-ins (it cannot tell the real person's from a thief's), the admin-reset notice can be dismissed by any session, and only the newest 50 notices per account are kept (at most 90 days), so very many sign-ins push an older notice out. None for public demo logins. |
| Notices as notifications (lock screen, push) | Android and the Mac also show a notice as a system notification while the app is closed or in the background (web: only if turned on, only while its tab is open). There is no push service (no Google/Firebase, no Apple push): Android's background task (WorkManager, about every 15 minutes when Android lets it run) and the Mac app while it runs (live updates; every 5 minutes while locked) ask the server themselves with the device's existing session cookie. No new credential is stored and no key is needed: notices are not encrypted, and the request is the same `GET /api/me/notices` the apps use to list notices, so the server's rule that a device is never shown the notice about its own sign-in applies unchanged. The request carries `X-CF-Background: 1` (GET only), so it is not counted as using the device: it doesn't keep a session past its idle end (30 days) or show the device as active in Account › Devices. On Android the notification and its channel are `VISIBILITY_SECRET` (with a public version for where Android redacts): it never shows on the lock screen, even when the phone's setting shows all notification content there, so the device's label and the time appear only once the phone is unlocked (a channel made by an older version keeps its own lock-screen setting, the notification's own secret visibility still applies); on the Mac the title names only what happened and macOS hides the body where it hides previews (the lock screen by default). The text is the in-app notice's (the device's own label and the time), never an IP address or a place. Each notice is notified at most once per device (the seen ids are kept on the device: the app's private files on Android and the browser's storage, both deleted at sign-out; the preferences on the Mac); a restore of the server moves the notice ids past every one it handed out before (to the time in milliseconds), so a notice after a restore is never taken for one already shown and only within 3 days of it happening. Limits: a notification shown with previews on reveals the device label to whoever looks at the unlocked screen; Android may delay or skip the background task (battery saving, Doze, aggressive vendor rules as on OPPO/ColorOS or Xiaomi, or a force-stopped app), so a notification can come late or not until the app is opened; on the Mac nothing arrives while the app isn't running. |
| Session theft / CSRF | `__Host-` cookie, HttpOnly, Secure, SameSite=Strict, CSRF token + Origin check, sessions are server-side rows that end 30 days after their last use (at most a year after sign-in; at most 50 per account, a new sign-in beyond that ends the one idle longest), and on sign-out, password change, recovery and account disable; Account › Devices lists them and signs out any one, and a device signed out that way deletes its local data at its next request. |
| Invite/setup abuse | Setup token printed to container logs, usable once, then permanently disabled. Invite tokens are 256-bit, stored hashed, single-use, expiring. An invite works only while whoever made it may still invite: one made by an administrator stops working when that administrator is demoted, disabled or deleted, and one made from a session stops when that session is signed out from the device list or ended by a password change on another device or an account recovery (so an invite made with a stolen session does not outlive it); the server console's invites depend on no account. |
| Phone with automatic backup lost or seized | The background backup holds only the account's public key and the session cookie: it can add photos, never read them. Thumbnails and the list are cached encrypted only; the master key stays in memory, or in the hardware keystore behind fingerprint/face if the person chose that, and leaves memory when the app has been in the background for the chosen time (immediately, 1, 5 by default, or 15 minutes) or, if chosen, when the screen turns off. The search index kept on the phone between unlocks is encrypted under a key derived from the master key. The phone can be signed out from another device (Account › Devices, or `sign-out --wipe` on the server), after which it deletes what it keeps at its next request. |
| Server inserts items | Items sealed to the public key (background backup) can be created by anyone holding that key, including a malicious server; they cannot be told apart from the phone's uploads. Reading the library stays impossible. The Android app never writes something it reads from the phone into such an item: the location added afterwards (docs/MAP.md) goes only into items this phone uploaded itself, with the wrapped item key it sent (kept on the phone by item id). Limit: the backup skips a phone file when the library already has one of the same name and size, so an inserted item naming a file's exact name and size keeps that file from being backed up; that needs the size of a file the server has never seen, and a malicious server can refuse to store uploads anyway. |
| What photos show, who is in them | Search runs on the phone (docs/SEARCH.md). Index entries are sealed to the account's public key, the people list is encrypted under the master key; the server sees only how many entries an account has, their padded sizes and when they were written. Favorites are a plain flag, like album membership: the server sees which photos are marked, not what they show. A malicious server could insert made-up index entries (as with sealed items) to make photos show up in the wrong searches; it cannot read any. The models are checked against SHA-256 values built into the app (see Search model downloads below). The explicit-content filter of search runs on the device from the vectors already there; nothing is stored or sent for it, so the server doesn't learn which photos it leaves out. The server sees each entry's model family in the clear (one for everyone now) and whether an admin allowed a person explicit search (`users.nsfw`), not whether they turned it on (that is in the encrypted people document). |
| Screenshots, screen recordings, recent-apps preview | A local-device matter: whatever is on screen is decrypted, and other apps, a screen recorder or the system's app switcher could keep a copy outside Cipherfilm. Android blocks all three by default (`FLAG_SECURE`, and from Android 13 the recent apps show the icon instead of the last screen), set in the activity's onCreate before its first frame, so the splash, lock and unlock screens and the library are covered alike. Account › "Allow screenshots" lifts it for that phone only (stored in the app's private preferences, not on the server; back to blocked at sign-out); it takes effect on the open window at once. The protection only stops other apps and the system's own captures: a camera pointed at the screen, a rooted or compromised phone, or accessibility services the person allowed still see the screen. The web app cannot block screenshots (no browser lets a page do that), and the Mac app does not try (macOS screen capture is up to the person's own screen-recording permissions). |
| Memories ("On this day") | Chosen on the device from the decrypted capture dates (web/src/memories, Android through the same file, Mac `Memories.swift`); no endpoint, no stored result, the on/off switch stays on the device. The server sees only the thumbnail requests for the cards' covers, the same requests the grid makes, so it can notice that a few older items' thumbnails are fetched early in a session; it never sees their dates. |
| Search model downloads | The apps download the open search models once from Hugging Face (docs/MODELS.md), not from the server, and only after the person agreed on that device (a question before every download of files not agreed to yet; no request to Hugging Face before it, enforced in each app's one download function and covered by tests). Hugging Face learns the device's IP address and that it downloaded these public files, nothing else: no cookie, account, photo or search word goes there. Every file is pinned to a commit and checked against a SHA-256 built into the app before it is opened, so neither Hugging Face, its CDN nor anyone on the way can swap a model. |
| Lost password **and** recovery key | Data is unrecoverable by design. The UI says so. |

## The hard limit: malicious JavaScript
In a web app the server delivers the code that does the encryption. **Anyone who controls the server (or the HTTPS proxy in front of it, or can modify the container image) can serve a modified client that exfiltrates the password or keys when a user next logs in.** E2EE here protects against passive compromise (disk theft, backups, a snooping admin who only reads data), not against an *active* malicious server operator. Users must trust that whoever runs the server does not ship altered code.

Mitigations (reduce, not remove):
- Strict CSP: no inline scripts, no `eval`, no third-party origins except `connect-src` to Hugging Face (`huggingface.co`, `*.hf.co`), from which the search worker fetches the text model as data, checked by SHA-256, never as code, and to the map's
  style hosts (OpenFreeMap and VersaTiles by default, or what the operator sets in `MAP_STYLE`, checked to be plain
  https hosts), from which MapLibre loads map tiles, fonts and icons as data once the person turned the map on; `'wasm-unsafe-eval'` only; `frame-ancestors 'none'`; `base-uri 'none'`.
- All assets self-hosted: no CDNs, external fonts, analytics or telemetry.
- Few, pinned dependencies with lockfile + integrity hashes; builds are not yet reproducible and no bundle hash is published.
- **Not implemented:** Subresource Integrity, service-worker pinning of the bundle hash and a published bundle hash. SRI on a same-origin script adds little against a compromised server, which serves the HTML too, so none of these would stop an active malicious operator; do not rely on the client to detect a swapped bundle.
- Pages are also sent with `X-Frame-Options: DENY`, for browsers older than `frame-ancestors`; the HEIC policy below applies only to files under `/heic/` after the path is resolved.
- Admin, as the person most able to ship bad code, is in the same trust position as the server operator; family members should know this.

### HEIC decoder exception
The WASM HEIC decoder (libheif, built with embind) constructs functions from strings, so it needs `unsafe-eval`. The page CSP stays strict. Instead the decoder runs in a dedicated worker file served only from `/heic/`, whose own CSP allows eval but sets `connect-src 'none'`: it receives file bytes, returns pixels, and cannot make any network request. Everything else (page, API, other workers) keeps the strict policy without eval. Residual risk: a decoder bug triggered by a hostile HEIC could misbehave inside that worker, but it cannot reach the network, the page, or any key.

### Service Worker
The Service Worker (`/sw.js`) decrypts video and big downloads. It is a single bundled script served with the normal strict CSP. It holds item keys only in memory, receives them from the page by message, and forgets them on sign-out. The `/sw/stream/` and `/sw/dl/` URLs exist only inside the worker; the server answers 404 for them, and no key ever appears in a URL.

### Deployment
The app needs a trusted HTTPS front: a reverse proxy the operator runs. Behind a proxy (`TRUST_PROXY=1`) it trusts exactly the last `X-Forwarded-For` entry, and only from a peer in `TRUSTED_PROXIES` (by default any loopback or private address, i.e. a proxy on the same host or Docker network; set it to the proxy's address to exclude other local processes and containers). `TRUST_PROXY=1` takes effect only together with `PUBLIC_HOSTS`: without a host allowlist a page on another name that resolves to the app (DNS rebinding) could choose its own `X-Forwarded-For`, so the header is then ignored and every client counts as the proxy's address. A private setup (Tailscale Serve) means trusting your tailnet's ACLs; there every client reaches the app from `127.0.0.1`, so with `TRUST_TAILSCALE_HEADERS=1` (the tailnet overlay) the per-source limits are keyed by the `Tailscale-User-Login` header Serve sets instead (only from a loopback peer and with `TRUST_PROXY` off; Serve removes a client's own; tagged devices get none and share one bucket); a public site adds exposure of the login and recovery endpoints, which are rate-limited per source address and per (account, source address), and per account only for known browsers; there is deliberately no per-account ceiling across all sources (see Brute-force login above), so use a strong password on a public instance.

## Other limits and non-goals
- Metadata (sizes, counts, times, album structure) leaks as listed above; metadata padding only blunts size leakage for small objects.
- Compromised client device or malicious browser extension defeats E2EE (keys live in memory there).
- XSS in the app would expose in-memory keys; mitigated by CSP, no `innerHTML` with data, and decrypted names rendered as text only.
- Browsers can keep decrypted blobs in memory / disk cache: we use `Cache-Control: no-store` on API responses and revoke object URLs.
- Denial of service by an authenticated user: storage is bounded by the per-user quota, which is reserved atomically before an upload body is read (a replaced thumbnail or preview, at most 3 MiB, is read first and only its growth is reserved, so it can be replaced at the limit with one no larger) and also covers thumbnails, previews, search index entries and the people list (only the model families and document names the apps use are accepted); each finished item is also charged the disk blocks its files take (whole 4 KiB blocks per file plus 4 KiB for its row and directory), so many tiny items cost what they take on disk; open unfinished uploads are capped at 50 per user. The quota check reads a per-account counter that the database keeps up to date with every write, so its cost doesn't grow with the library and one account's large library doesn't slow other accounts' uploads. List pages (`/api/items`, `/api/trash`, `/api/index`) stop at about 4 MiB of encrypted data, at most 4 of one account's pages are built at a time, and a client that stops reading one is cut off after 5 minutes. Request headers must arrive within 10 seconds and bodies within a deadline (30 seconds for JSON, 15 minutes per upload part); the number of connections is not capped by the app, so a fronting proxy should limit it.
- Two-step sign-in is optional and off by default: without it a stolen password is enough to sign in. In a private tailnet setup the thief also needs a device on the tailnet; on a public site the login is reachable from anywhere.

### Two-step sign-in (TOTP): what the server knows
TOTP (RFC 6238, the codes authenticator apps show) is a shared secret: **the server must know the secret to check a code**, so it can also make codes. It keeps the secret encrypted (AES-256-GCM, bound to the account and to "pending" or "on") under a key derived from its own secret file (`data/secret`), so a copy of the database alone (a leaked `app.db`, a database dump) doesn't reveal it. Whoever has the database *and* the secret file (the server's own backups contain both), or runs the server, can make codes. That is no new power over the photos: such an operator could already serve modified web code (see above), and two-step sign-in never takes part in encryption — the password alone still derives the keys, so it protects the account's sign-in, not the data at rest. The QR code with the secret is drawn on the device (no QR service sees it); the secret is shown once at setup and is never sent again.

### Passkeys: what the server stores and learns
A passkey (WebAuthn) can stand in for the code at the second step; it never stands in for the password, which derives the keys, so a stolen passkey alone gets nowhere, and two-step sign-in with only passkeys is still "password and something you have". The flow keeps every guarantee of the code step: the password step returns only the pending token; `POST /api/auth/login/2fa/passkey` gives that pending sign-in one challenge (a newer one replaces it), and any check of the pending sign-in, right or wrong, uses it up, so an answer can't be replayed, nor sent for another pending sign-in or a signed-in session's own challenge (those are kept per session). Wrong answers count like wrong codes (5 per pending sign-in, 5 per account per 15 minutes, 20 per day). The relying party is the name the request reached the server by, never an address, and one of `PUBLIC_HOSTS` when that is set: a passkey is made for one name and only accepted there (the browser's origin must be `https://<name>`, the authenticator signs over the name's hash). A signature counter that doesn't move forward is refused (a copied security key; synced passkeys always send 0), and the new counter is stored only if the record is still the one that was checked. Adding a passkey needs the password and, while two-step sign-in is on, a second step (a code, a recovery code or another passkey), so whoever has an open session, or a session and the password, can't add a second step of their own; whether it is on is checked again when the new passkey is stored, so a registration begun while it was off can't be finished after it was turned on. The same holds for an authenticator app: its setup records whether a second step was checked for it and when it was made (sealed with the secret), is good for 15 minutes, can't be finished once a passkey turned two-step sign-in on unless it was checked, and is dropped when a passkey is added or the password changed or recovered. Removing a passkey needs the same; removing the last second step also ends the session challenges begun under it. Limit: an older server version doesn't know passkeys, so going back to one lets accounts with only passkeys sign in with the password alone (not supported, docs/RELEASING.md). The first second step makes the recovery codes; removing the last one (and no app) turns two-step sign-in off and deletes them; an administrator's or the console's reset, and turning it off, remove the passkeys too.
- **Server stores**, per passkey: a random id, the credential id, the name it was made for, the name the person gave it, when it was made and last used, and the credential record (public key, signature counter, transports, authenticator model AAGUID, backup flags), the record encrypted under a key derived from the server's secret file and bound to the account and credential id, so a copy or an edit of the database alone can neither read the record nor add or move a passkey. The user handle given to authenticators is the account's random id; the account's e-mail is the name the authenticator shows.
- **Server learns**: when a passkey is used, and from the records which kind of authenticator someone uses (the AAGUID names a model or a password manager) and whether it is synced. No attestation is asked for, so nothing identifies the device itself. No PRF/hmac-secret is asked for: a passkey takes no part in encryption.
- **Android**: the app's origin is `android:apk-key-hash:` and its signing certificate's SHA-256; the server accepts only the certificates in `ANDROID_APP_CERTS` (default: the official release key, which Play signs with too) and lists them with the packages in `/.well-known/assetlinks.json`, which Android checks before it lets an app use a passkey of the server's name. An app signed with another key can't. Android checks the file through Google, so passkeys on Android work only when the server's name and that file are reachable from the internet; a tailnet-only server keeps the code. Credential Manager is the system's own from Android 14; older phones keep the code (the app brings no Google Play services).
- **Android, private servers**: Google checks `assetlinks.json` from the internet before Android lets an app use a domain's passkeys, so for a server it can't reach (a tailnet `*.ts.net` name, a private or LAN address, `.local`/`.lan`/`.internal`, or one Android refused before on this phone) the app uses the server's `/passkey` page in the browser, as the Mac does. The options go in the address's fragment (never sent to the server); the page returns the answer only to a fixed address per app (`cipherfilm://passkey`, `cipherfilm-test://passkey` for test builds; the page never takes a return address from the fragment). Another app registering the same scheme could receive that answer; it is bound to a challenge the server issued for this app's pending sign-in or signed-in session, valid minutes and once, and useless without that session or pending token, which stay in the app.
- **Mac**: a Mac app can use passkeys only of the names Apple ties to it when it is built (Associated Domains), which can't list self-hosted servers, so the app opens the server's own `/passkey` page in a sign-in window (`ASWebAuthenticationSession`, the default browser). The options go in the address's fragment (never sent to the server), the browser asks for the passkey on the server's real origin, and the page hands the answer back to `cipherfilm-mac://`, which only that waiting window receives. Limit: a link to that page sent by someone who has the password (and so a pending sign-in and its challenge) can make the person's browser ask for their passkey; the answer then goes to the `cipherfilm-mac:` address, which outside the app's sign-in window reaches only an app registered for it (the Cipherfilm Mac app registers none), so it would take a malicious app on that computer as well. The page says to continue only if the sign-in was just started on the Mac.
- **Web**: the page asks `navigator.credentials` with the server's options; the strict CSP is unchanged (no new origins, no inline script).
- In a private tailnet setup the tailnet's ACLs are the first line of defence (only intended devices reach the host). On a public site only the login rate limits and the Argon2 cost stand in front of the accounts. Either way the app does not trust the network.

## Residual-risk summary
Strong against: data-at-rest compromise, curious admin, cross-user access, ciphertext tampering. Not strong against: a malicious server operator shipping hostile JS, a compromised user device, weak passwords combined with a stolen database.
